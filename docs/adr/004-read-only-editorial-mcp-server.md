# ADR 004: Read-Only Editorial MCP Server over the Service-Role Key

We're adding a local MCP server at `/mcp` (stdio, `@modelcontextprotocol/sdk`) so Claude Desktop can answer editorial questions from live data. It exposes four read tools: `held_stories`, `brief`, `gate_failures` and `story_trace`. It connects to Supabase with the service-role key from the environment. That key bypasses row-level security, so "read-only" can't depend on database permissions, and the server enforces it in the process. Product scope is PRD-71. This ADR records how read-only is guaranteed and how the tools map onto the live schema.

Context: the service-role key is the only credential that can read every editorial column (`decision_note`, validation details, unpublished drafts). The anon and publishable keys only see public rows. A mistaken or prompt-injected tool call running as service role could write to production, so the server needs a guarantee that holds even if its own code or a future tool is wrong.

Read-only is enforced in three layers. (1) The database handle exposes only `select`, so nothing in the server can call insert, update, upsert, delete or rpc. (2) Only four tables can be named: `signal_posts`, `pipeline_article_candidates`, `newsletter_story_extractions` and `newsletter_emails`. (3) The Supabase client gets a custom `fetch` that rejects any request whose method isn't GET or HEAD. PostgREST reads are GETs. Writes and RPC calls are POST, PATCH or DELETE, so they fail before they leave the process. Layer 3 is the one that holds against future code mistakes, and a unit test pins it.

Alternatives we considered. A dedicated read-only Postgres role with a direct `pg` connection would enforce read-only at the database, but it needs a database password that this project doesn't have and a new role in production. That's the stronger long-term option. Using the publishable key under RLS was rejected because it can't see held, draft or gate-failed rows, and those are the whole point of the tools. Wrapping hand-written SQL through an RPC was rejected because RPCs are POSTs and the task forbids them.

Schema mapping, from inspecting the live schema. There is no "folded" decision value: a fold is `removed_from_slate` with a `decision_note` starting "Folded". The gate validates only `why_it_matters`. `signal_posts` has no foreign key to its ingestion row, so `story_trace` joins RSS rows on `pipeline_article_candidates.canonical_url = signal_posts.source_url` and picks the latest ingestion on or before the briefing day. Newsletter rows join through `newsletter_story_extractions.signal_post_id`. `brief` reuses the homepage's public-card rule so it can't show a card the site wouldn't. The legacy or empty tables (`story_clusters`, `story_cluster_members`, `daily_briefings`, `events`, `published_slates`) aren't allowlisted.

Consequences we accept. The URL join can match several ingestion runs, and the tool reports how many. Fold detection depends on an editorial note convention, not a column. The server runs only on the editor's machine and isn't deployed. Revisit this if a remote (HTTP) transport is ever added, if a read-only database role becomes available, or if folds get their own `editorial_decision` value.
